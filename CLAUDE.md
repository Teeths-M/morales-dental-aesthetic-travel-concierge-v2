## The M Principle — Non-Negotiable

> "We built this to save lives, not to make profit."

**RED is a hard block. Always.** No bypass button, no workaround, no exception for any business reason.
If a procedure combination is clinically dangerous, M will not facilitate it — full stop.
The client can book elsewhere. M will not be the platform that put their life at risk.
This principle must never be softened, worked around, or compromised in any feature, edge case, or demo.

## Safety-Decision Architecture — Invariants (do not regress)

The AI/narration layer has **no technical capability to approve, reject, or modify a safety decision.** Only deterministic engines write safety outcomes. Established 2026-07 (commit `45647208`); a CI red-team guards it.

- **Deterministic decides, AI narrates.** The patient SAFE-T risk level is computed only by `base44/functions/_shared/safeTEngine.ts` (`computeSafeT` — pure, replayable). `computeSafeTScreening` writes the decision to the append-only, hash-chained `SafeTScreening` entity **first**, then invokes the LLM only to narrate it — the LLM receives just the finalized `risk_level` + flags (never raw patient text) and any risk level it returns is discarded. Never move SAFE-T scoring back into an LLM or into the client.
- **Fail closed.** Ambiguity, incomplete profile, pregnancy, or detected prompt-injection → `review` (needs human review), **never** `low`. `SafeTScan.jsx`'s error fallback is `review`.
- **The RED block stays deterministic** (`validateProcedureSafety` → `_shared/procedureCompatibility.ts` `getViolations`, re-checked server-side). `checkMedicalRisk` (admin-review routing) and `runMedGuardAnalysis` (in-travel score) are deterministic too. AI cannot suppress or override any of them.
- **AI may raise caution, never clear it.** In any hybrid scorer the LLM may only *add* risk. `runInternetIntelligence`'s AI can flag but not lower a score. The clinic agent (`verifyClinicStatus`) may auto-*block* (`closed`) but never auto-writes the permissive `operating` — it routes that to a human (`agent_proposed_operating`).
- **Doctor-verified completion + memory bank** (`logProcedureComplete`, `_shared/procedureMatch.ts`, `writeOutcomeMemory`, `recallSimilarOutcomes`): `computeProcedureMatch` deterministically compares booked vs. doctor-confirmed procedures — a mismatch is flagged (`mismatch_flagged`) for human review, never silently resolved, and an LLM may only narrate the already-decided status. Doctor-entered `doctor_recommended_medications` (never AI-generated) feed an anonymized `OutcomeRecord` (category/condition tags only — no patient identity, no raw med text). `recallSimilarOutcomes` surfaces that history back only as **doctor-only** aggregate advisory context (never patient-facing), always carrying a fixed caveat in the payload itself — it informs a doctor's own judgment and writes nothing back automatically.
- **Sanitize all user text reaching a prompt** via `base44/functions/_shared/sanitizePromptInput.ts`; an injection hit on the safety path forces `review`.
- **Log decision + narration** to the `SafeTScreening` `prev_hash` chain. Append-only — never update/delete.
- **Red-team gate.** `tests/redteam/safety-redteam.spec.js` (Playwright `redteam` project) runs deterministically, no network/credits; `.github/workflows/redteam.yml` re-runs it on every change to `base44/functions/**/entry.ts` (catches model-version changes) and weekly. Changing a model ID or the engine must keep it green.

## Data Freshness — fail-safe, not fail-silent

Time-sensitive status (clinic operating, doctor licence, visa, regulatory) is governed by `base44/shared/freshness.ts` (per-type TTLs + `flagForReview` → the `DataFreshnessReview` human queue). Cached status is never served as confirmed past its TTL — it is re-verified or clearly labelled unconfirmed. Clinic bookings gate on `checkClinicStatus` (blocks unless operating **and** fresh; soft-labels until `CLINIC_GATE_ENFORCE=true`). Scheduled by `.github/workflows/freshness-cron.yml`, guarded by `shared/cronAuth.ts` (cron secret **or** admin session). Admin surfaces: `/admin/clinics`, `/admin/data-freshness`.

**Curated country-data auto-refresh — the one deliberate auto-publish exception.** `src/lib/visaMatrix.js` (`EXPLICIT_ROUTES`, `EVISA_LINKS`) and `src/lib/travelReadiness.js` (`PASSPORT_RENEWAL_LINKS`) are hand-curated JS constants with no TTL of their own (distinct from the live `VisaRequirementSnapshot` cache above, which does have one). `.github/workflows/curated-data-refresh.yml` runs **monthly**, invoking Claude Code directly (`anthropics/claude-code-action`, real `WebSearch`/`WebFetch` tool access — not Base44's `InvokeLLM`, which already produced one wrong visa answer for a real patient and is why the curated matrix outranks it) to re-verify every entry against the live web and auto-commit any confirmed fix straight to `main` — the one place in this repo where an AI-driven change ships without a human confirming first, deliberately mirroring the trust model already extended to `base44-builder[bot]`'s direct commits (reviewed after the fact, not gated before). Guardrails: a deterministic post-run `git diff` check discards the commit if anything outside those two files changed; the commit only survives if `build`/`vitest`/`redteam`/`typecheck` all still pass; the agent is instructed to never fabricate a URL and to leave anything it can't confidently verify untouched. Every outcome (applied, or a gate/scope failure) is logged via the new `logCuratedDataRefresh` function into the same `DataFreshnessReview` queue (`subject_type: 'passport_renewal_link'` added for this) — applied changes land pre-`actioned` (transparency, nothing to decide), failures land `pending`/`critical` like any other real flag. Needs a one-time `ANTHROPIC_API_KEY` GitHub secret (skips harmlessly, green, if unset) — see the workflow file's own header for full setup.

## Travel Safety Escalation — "no human touch needed" partner/patient recovery

Every scheduled job below runs from `.github/workflows/safety-cron.yml` (15-min tick, hourly, 6-hourly, and a daily 09:00 UTC deployment audit that fails loudly on anything undeployed) — **not** Base44's own scheduler, and **not** an admin clicking a button. This file's own header documents a recurring bug class worth knowing before adding a new scheduled function: real, correct code that nobody ever actually scheduled, or that required a live admin session (which a cron tick can never hold). This has bitten `checkPartnerSLABreaches`, `dispatchSoloSecurity`, `scheduleSoloCheckIns`, and `detectFallbackCrisis` — each existed, worked, and protected nobody until fixed. Any new scheduled safety job must (1) gate on `_shared/cronAuth.ts`'s `cronAuthorized()`, never `base44.auth.me()` + a role check, and (2) actually appear in `safety-cron.yml`, not just in its own header comment describing an intended cadence — trust the workflow file, not a function's self-description of when it runs.

- **Partner never responds to being offered a job** (doctor, driver, travel agency, companion) — `checkPartnerSLABreaches`: 24h → auto-dispatches a backup, 48h → human-intervention alert. For doctors specifically, this used to be a silent swap — the original doctor got no warning before being replaced. Added 2026-08-05: at the 12h halfway point, a reminder goes to the doctor on every channel we have for them — link-only email always, plus SMS/WhatsApp/in-app push where a phone or push subscription exists (`doctor_email` + their existing `doctor_portal_token` portal link, gated by a new one-time `doctor_reminder_sent_at` field) — so the 24h auto-backup is a deadline they were actually told about, not a surprise. Content and channel selection live in `base44/shared/doctorReminderCopy.ts`, translated into the doctor's `language_preference` (9 languages matching `src/i18n.js`'s `SUPPORTED_LANGUAGES` — `tr`/`th`/`zh` were added to `Doctor.jsonc`'s enum the same day specifically because M has doctors in Turkey/Thailand who may not read English). All channels stay link-only/generic (no patient name, no date/time) — same rule as everywhere else in this file; the real detail is only ever in the portal behind the link. One real caveat: the in-app push only reaches a doctor who has logged into the full dashboard at least once — the magic-link `/portal/doctor/:token` page these reminders link to has no auth and no push subscription of its own, so a doctor who only ever uses that link won't get pushed, same as before this change.
- **Partner drops after already confirming** (doctor withdraws, driver/companion cancels) — three shared, reusable finders: `base44/shared/{findDoctorBackup,findDriverBackup,findCompanionBackup}.ts`. Each finds the next verified/licensed replacement, reassigns the case, and alerts admin; if none is available it's a loud critical email + `DispatchFailureLog` entry, never a silent status flip. `findDoctorBackup` additionally escalates to an SMS (`ADMIN_PHONE`) and a link-only FYI to the travel agency/companion already on that trip when the patient is already traveling (`departure_date` passed or `procedure_date` within 72h).
- **Doctor still unconfirmed as the procedure itself approaches** — `detectFallbackCrisis` previously only checked confirmation *speed* (15 minutes after being notified, `CONFIRMATION_WINDOW_MS`); a doctor notified early who simply never got around to confirming, with the patient already on the ground, was invisible to that rule. Added 2026-08: a second, independent check — `doctor_confirmation_status` still `PENDING` with `procedure_date` within 24h flags the case urgent (same `fallback_state` shape); within 4h additionally fires an admin SMS, not just the flag; the 24h tier also reminds the doctor directly on every channel (email/SMS/WhatsApp/push, translated — same `sendDoctorReminder`/`doctorReminderCopy.ts` pattern as `checkPartnerSLABreaches` above, added 2026-08-05) so the doctor has a real chance to confirm before admin is ever pulled in at 4h. Deliberately does **not** auto-call `findDoctorBackup` at either tier — "hasn't confirmed yet" is a softer signal than a driver physically failing to show, and unilaterally reassigning a doctor who may still come through risks real harm (duplicate assignment, a doctor arriving to find they've already been replaced); a human decides, with the real backup-finder one click away in the admin console. `detectFallbackCrisis` itself was also a real, correctly cron-auth-guarded function that had simply never been added to `safety-cron.yml` — another instance of this section's own recurring bug class — now scheduled in both the 15-minute and daily blocks. **Deliberately deferred, same session**: companion meet-up confirmation has the identical shape of gap (`DigitalHandshake.jsonc`'s `checkpoint_type` enum already declares `companion_departure_airport_confirmed`/`companion_arrival_airport_confirmed`/`companion_clinic_arrival_confirmed`/`companion_hotel_arrival_confirmed`/`companion_recovery_instructions_received`, and `CompanionHandshakePanel.jsx` can list/complete them — but nothing anywhere ever creates one, and `CompanionAssignment.status`'s `active`/`completed` values are declared but never written). Real, bigger feature than this fix — new checkpoint-creation wiring across 5 trip stages, a no-show detector, and a `findCompanionBackup` hookup — scoped for its own future session, not rushed in alongside this one.
- **Driver no-show at any pickup/dropoff leg** (the 9-step journey in `completeHandshake/entry.ts` — steps 1/3/5/7/9 each need a driver) — `escalateMissedDriverHandshake` checks `TravelRequest.scheduled_departure` (step 1) or the prior step's confirmed timestamp (steps 3/5/7/9); 30 minutes overdue with no confirmation dispatches a backup driver via `findDriverBackup` and texts the patient directly (the one case where texting the patient proactively is correct — they're already watching no car arrive, so "we see it, help's coming" is reassurance, not bad news). Idempotent via `TravelRequest.noshow_flagged_steps`.
- **Patient goes silent / phone dies** — `scheduleSoloCheckIns` creates a check-in for every actively-traveling case, only once it's actually due (first at 6h post-intake-handshake, then every 12h — it used to fire the moment it noticed the case, ignoring both numbers; covers solo **and** companioned travelers — a companion nearby doesn't guarantee M can reach the patient). `escalateSoloCheckIn` runs the ladder: **2h → guardian notified** (email + SMS + WhatsApp if a phone is on file, each with a live link to the same Google-Map `GuardianView` used at every later tier, so they can see the patient's location and reach out themselves at the first missed check-in, not the third) → 3h → voice call attempt + satellite fallback to the patient → 5h `dispatchSoloSecurity` (real SMS handshake with a security agency, tries the next agency if unconfirmed in 15 min, loud failure if every agency is exhausted) → 9h police/embassy escalation. `checkStaleLiveLocations` is a parallel, consent-gated GPS-staleness check. **Guardian contact fields, read this before touching any of them**: `CaseRecord.emergency_contact` is a display label only ("Jane Doe (Spouse)"), never an email or phone — the real fields are `emergency_contact_email`/`emergency_contact_number`, synced from `PersonalEmergencyContactsPanel.jsx`. Both `escalateSoloCheckIn`'s guardian email and `completeHandshake`'s milestone Guardian SMS were silently reading the wrong field for months (the label, or a `guardian_phone` that was never written) — fixed, but a fresh reminder that a field name matching what a comment *says* it holds isn't proof it does.
- **The guardian isn't just notified, she can act.** `GuardianView.jsx` (`/guardian/:token`) has a "Reach Out" panel with real `tel:`/`sms:` links to the patient and their doctor, the local country emergency number (from `EmergencyContacts` — real entity, but currently has **no seeded rows for any country**; the button simply doesn't render until one exists for a given country), and a "Request Immediate Security Check" button. That button calls `requestGuardianSecurityCheck` (token-verified, same `GuardianSession` check as `getGuardianViewData`) which invokes `base44/shared/dispatchSecurityForCheckIn.ts` — the exact same dispatch logic `dispatchSoloSecurity`'s 5h cron sweep uses, extracted so both callers share one verified implementation. Deliberately does **not** hand the guardian a security vendor's raw phone number — she directs M's system, M stays the one actually contacting the agency.
- **Known, deliberately unfixed gap**: a companion who accepted an assignment then silently vanishes mid-trip (no explicit cancel) has no detection today. `MealDelivery.status` has the right shape (`scheduled → en_route → delivered`) but no live writer anywhere — building a detector on it would just be false alarms. Needs a real confirmation action (companion or patient side) before this is closeable.
- A second, more granular escalation engine (`runSilentSafetyEscalation`, 15m/30m/60m/120m/180m ladder) exists but is **not** scheduled anywhere — admin-button-only via `AdminSoloMonitor.jsx`. Don't assume it runs; a comment in `submitRecoveryCheckin/entry.ts` claims it does and is wrong.
- **Same bug class, event-triggered instead of cron-triggered**: `storeSafetySignal` (feeds the anonymized `SafetySignal`/`SafetyIndexCache` "Safety Intelligence Network" behind MedGuard's "gets more predictive over time" claim) had zero callers anywhere — its own doc-comment claimed HS9/`closeEmergencyThreatLoop`, neither ever called it. Fixed 2026-08-04: wired into `completeHandshake`'s HS9 block with real per-trip data (SOS events, escalated check-ins, MedGuard audit-log risk history). A useful diagnostic for finding more of these: grep every function name in `base44/functions/*` against the whole repo (frontend, other functions, workflows) — anything with zero hits outside its own `entry.ts` is a real dead-end candidate, though verify each by hand before touching it. ## Struggle-Aware Recovery ("M Rescue")

Detects someone stuck or abandoning signup and offers help before they quit — deterministic detection, never AI deciding anything, and never AI-personalized outbound messages (see the link-only rule below). Two independent halves:

- **In-session**: `src/hooks/useStruggleDetector.js` watches a field for two signals — idle-while-invalid past a threshold, or N consecutive failures (both pure/testable via `shouldArmIdleTimer`/`shouldFireRetryFail`, no network). On either, the caller emits a hint via `src/lib/struggleHint.js`'s `emitStruggleHint(emoji, text)` — a window-event bridge (same pattern as `i18n.js`'s `languageChange`) to `MCareOrb.jsx` ("M-Care"), the one floating assistant, since struggle signals originate deep in arbitrary forms while the orb is a singleton mounted once in `AppLayout` (plus the two partner-portal pages below). The hint pre-empts the orb's normal timer-based tip rotation and clears on route change. Wired into `Login.jsx` (phone/OTP); `DoctorSignup.jsx`/`TravelAgencySignup.jsx` are wired for the abandon-tracking half below but not yet this in-session half.
- **Post-abandon**: signup forms already call `saveSignupDraft(type, formData, {step})` (`src/lib/signupDraft.js`) on every step change, purely to localStorage. `trackSignupProgress(type, data, step)` piggybacks on those exact call sites — fires at most once per step, only once a phone or email exists in the draft — POSTing to `trackSignupAbandon` (public, `bodySchema`-validated, writes only via `asServiceRole`; `SignupProgress` has **no client-readable/writable RLS**, admin-only, same reasoning as `AccountFlag`). `checkStalledSignups` (Base44-dashboard cron, `cronAuthorized`) finds records stale 30+ min and sends **one** recovery nudge.

**M-Care consolidation (2026-08-05).** This app used to run three separate, unconnected AI assistant personas at once — "Morales Guide" (a bottom-left tip/Q&A orb), "Morales Assist" (a bottom-right general-concierge chat + human handoff), and, on one page, "SAFE-T VISA ASSIST™". On `/visa-assist` a logged-in patient could see all three assistant surfaces simultaneously — real clutter, and a name collision waiting to happen. Guide and Assist are now one component, `src/components/mcare/MCareOrb.jsx` ("M-Care") — same bottom-left position and hero-collision math Guide already had tuned, same KB-first/tip-rotation/quiet-route/struggle-hint behavior verbatim, but a logged-in non-admin user whose question misses the KB now falls through to the real, case-aware `moralesAssist` edge function (which can hand off to a human specialist) instead of the old generic platform-Q&A LLM call. Mounted in `AppLayout.jsx` (universal except demo routes — same condition Guide had, deliberately not narrowed to logged-in-only) plus `PortalTravelAgency.jsx`/`PortalDoctor.jsx` (the two partner magic-link pages that mounted Guide independently). M-Care only ever narrates — it has no write access to any SAFE-T/procedure-compatibility decision or intake data. SAFE-T VISA ASSIST™ (`src/components/visa/VisaAIChat.jsx`) deliberately **stays a separate identity** — its compliance-footer branding reads as a deliberate sub-brand, a call for Portia not an engineering default — but its real privacy bug got fixed regardless: it was calling `InvokeLLM` directly from the client with no PHI scrubbing and no real rate limit (its `MAX_MESSAGES`/3-second cooldown was only JS state, trivially bypassed), bypassing a backend function that already existed for exactly this (`base44/functions/safeTAssist/entry.ts`, deliberately unauthenticated, IP-rate-limited, and already redteam-exempted — but until this fix had zero real callers anywhere in the repo). `safeTAssist`'s own hardcoded system prompt is a *different* persona ("Safe-T4life", general journey/safety Q&A) — routing visa questions through it unchanged would have answered them in the wrong voice, so the fix added a `topic: 'visa'` request field that swaps in a visa-specific system prompt while sharing the same scrub/sanitize/rate-limit pipeline both personas need. Also fixed in passing: `VisaAIChat.jsx`'s own source had mojibake-corrupted UTF-8 (™, em dashes, emoji all garbled) in its user-visible strings — a real, visible bug, cleaned up while the file was already open for the backend-call fix.

## M-Care super-agent, Phase 10 — root cause of a fully silent agent, and a safety net for the next one (2026-08-08)

Immediately after Phase 8 shipped, M-Care went completely silent for Portia — a message would send, the "coordinating" indicator would clear, and nothing would ever come back. No error, no reply. Root cause: Phase 8 added `mcareCreateDoctorPending`/`mcareCreateTravelAgencyPending` and registered them in `m_care.jsonc`'s `tool_configs` in the same commit — but per this file's own Deploying & Environment section, a repo push only *syncs* code into the Base44 Builder, it doesn't make it live; new edge functions need a separate Publish. The two functions existed in the repo and in the agent's declared toolset, but weren't deployed yet, and the agent's tool-resolution step appears to fail the *entire* conversation turn when a declared tool doesn't actually exist server-side — silently, with nothing surfaced back to the chat UI. Portia found and fixed this herself directly in Base44 (confirmed via both functions now returning 400-needs-params instead of 404-not-found when pinged, and the agent replying normally again).

**The durable lesson, not just this one incident**: adding a new function to an agent's `tool_configs` is a two-step operation with a real gap in between — pushing the code and registering the tool name is not the same as the tool existing yet, and unlike a normal broken API call, the failure mode here isn't a clean error, it's the agent going fully mute. Any future M-Care backend function addition needs the same order of operations Phase 8 skipped: deploy/Publish the function *before* (or atomically with) wiring it into `tool_configs`, and verify with a direct ping (expect 400/401 for "exists, rejects bad input," not 404) before trusting the agent to use it.

**Fixed in the same pass**: while investigating this live, a real defense-in-depth gap was found — `sendAgentMessage`'s and `startNewJourney`'s catch blocks in `MCareOrb.jsx`, and the equivalent ones in `MCareAgent.jsx`, swallowed any send/create failure with no user-facing feedback at all. Wired in `src/lib/friendlyError.js` (the existing, established utility for exactly this — turns a raw error, including Base44's own documented 402 integration-credit gate, into a safe sentence; already used the same way in `ConsultationFeeModal.jsx`) via a `toast`, so *any* future cause of a failed send — not just an undeployed tool — surfaces something to the user instead of dead silence. Portia independently shipped her own, better version of the same idea directly in Base44 the same day: the conversation subscription now only clears the "sending" spinner once an actual assistant reply lands (not just on any update), a 12s safety-net re-fetch catches a subscription that missed the agent's turn, and a 40s last-resort timeout posts an honest in-chat fallback message. Both landed together via a real (successfully reconciled) merge conflict on this exact file.

## M-Care super-agent, Phase 12 — a real QR code inside the chat itself (2026-08-08)

Portia tested M-Care live right after the Travel Pass card above shipped and asked it for a QR code a driver could scan to get back to her hotel. The build reused an existing, proven mechanism rather than inventing a new one: `MessageBubble.jsx` (the one message-rendering component both `MCareOrb.jsx` and `MCareAgent.jsx` already share) already parses a `{{maps:LABEL|DESTINATION}}` token M-Care emits into three tappable Waze/Google/Apple buttons, built via `mapLinks.js`'s `generateMapLink()` — a token the agent emits itself, with **no backend tool call involved**. ## M-Care super-agent, Phase 18 — Talk Mode: auto-speak, word-sync, voice toggle for the buildathon demo (2026-08-08)

Portia sent a detailed 3-part spec for a full demo-day voice experience: M-Care auto-speaks every reply, text streams word-by-word in sync with the speech, and the whole thing is toggleable by natural voice/text commands ("toggle talk mode", "speak to me", "stop talking"). **Deliberately built on `window.speechSynthesis` (Web Speech API), not a server call** — matches Portia's own explicit preference ("Recommended for reliability... no API keys needed"), and is the right call independent of that: zero network dependency once the page has loaded, so a dropped WiFi connection on stage can't kill the demo. **`MessageBubble.jsx`** gained one new optional prop, `revealUpTo` (a word count). A separate effect stops any Talk Mode speech the instant the microphone starts listening, preventing a feedback loop. Turning Talk Mode off mid-speech stops audio and snaps the in-progress message to full text immediately, never leaving it half-spoken.

No separate "Demo Mode" flag — Talk Mode's rate is hardcoded to the same 0.9x her demo-clarity spec asked for regardless, since there's no real distinction between "the demo" and "someone actually wants to hear replies out loud." Talk Mode state is in-memory only, resets on page reload — not persisted to a user profile. ## M-Care super-agent, Phase 19 — Conversational Mode: always-listening, barge-in, honest interruption handling (2026-08-08)

Portia sent a detailed spec for "real-time conversational voice with barge-in" — an always-listening mic, the ability to talk over M-Care mid-reply and have it stop immediately, spoken "let me look that up" acknowledgments while a tool runs, gentle silence prompts, and "context-preserving interruption" (M-Care voicing both the new answer and a finished version of the interrupted one, unprompted, in a single woven reply). Explicit closing instruction, matching Phase 18's: don't break anything.

Went through Plan Mode for this one rather than building directly — the spec was written without checking it against this app's actual architecture (an AI-generated pitch, the same pattern as several prior asks in this file), and before proposing anything it was worth confirming what the platform can actually do. Read `node_modules/@base44/sdk/dist/modules/agents.js` directly — Base44's real `subscribeToConversation` is a WebSocket room that delivers one full message at a time (matched and replaced by id), not a token stream. **That one fact reshapes the whole feature**: by the time any text exists to speak, the agent has already finished generating the full reply — there is no way to stop the AI "mid-thought," only to stop the client-side playback of an already-finished reply. Everything below is built honest to that constraint rather than pretending otherwise.

**Shipped**: `src/lib/conversationalMode.js` (new, mirrors `talkMode.js`'s pure-helpers-plus-one-isolated-lifecycle-function shape) — `isConversationalModeSupported()` gates the whole feature behind both `SpeechRecognition` (input) and `speechSynthesis` (output) being present, which excludes Firefox entirely (zero `SpeechRecognition` support) — an accepted gap, not a bug, matching the same tradeoff `VoiceInputButton.jsx`'s own header already documents for push-to-talk. `startContinuousRecognition()` wraps `SpeechRecognition` with `continuous:true`, auto-restarting (capped, with backoff) since browsers stop continuous recognition on their own silence timeout despite the flag. `createBargeInDetector()` requires several consecutive, non-shrinking interim results before confirming a real interruption — standard `SpeechRecognition` gives no volume/energy signal, only recognized text, so a single stray syllable bleeding through the speaker (imperfect echo cancellation without headphones is a real risk) could otherwise look identical to a real barge-in; the thresholds are deliberately named/exported constants Portia will need to retune after testing on real hardware, not tuned values presented as final. `classifyInterruptionUtterance()` recognizes "never mind" (drops every pending topic) and an anchored-prefix "no wait, I meant..." correction (drops just the topic this exact interruption pushed) versus the default new-topic case — exact/anchored matching only, so "I mean, is that safe?" mid-sentence is never mistaken for a correction, the same discipline `talkMode.js`'s phrase matching already uses.

**Wired into `MCareOrb.jsx`** (the floating "M-Safe" panel, same scope Talk Mode shipped to — not yet `MCareAgent.jsx`'s full-page surface): a new phone-icon toggle in the header, off by default, additive to (never replacing) existing typed input and push-to-talk. Turning it on also turns Talk Mode on (a silent phone call makes no sense); turning it off leaves Talk Mode as the user left it. Mic ownership is resolved by simply not rendering `VoiceInputButton` while Conversational Mode is on, rather than trying to make `MediaRecorder` and `SpeechRecognition` coexist — there's no real scenario needing both, and whether they can safely share a mic isn't verifiable from this checkout anyway. Barge-in gets its own effect, completely separate from the existing push-to-talk anti-feedback effect (`if (listening) stopSpeaking()`), so neither was touched. Interim results live-fill the existing input box during normal turn-taking (satisfies "streamed interim results" with zero new UI); a confirmed barge-in stops audio, snapshots what M-Care was cut off saying, and flashes the orb (`LivingOrb.jsx` gained an optional one-shot `flashToken` ring pulse, replayed via a `key` remount — additive to its existing four-state `state` prop, not a new looping state). The header avatar swaps from the static `McareAvatar` to the live `LivingOrb` only while Conversational Mode is on, so its listening/thinking/speaking/flash states are actually visible during a call — the closed floating button already showed `LivingOrb`, but the open panel's header never had before now.

**The one honest reframe, called out explicitly rather than shipped as a silent downgrade**: the spec's "context-preserving interruption" has M-Care voicing both topics unprompted in one woven reply. Building that would mean either injecting hidden text into what gets sent to the agent, or literal words into the user's own chat bubble that they never said — and it would only work if `m_care.jsonc`'s giant instructions field reliably learned a brand-new convention with no way to verify it before Publish. That file has already caused one real outage this project (Phase 10's undeployed-tool silence), and no `m_care.jsonc` change of any kind was needed for anything else in this feature — spoken tool-call acknowledgments reuse the `display_projection.active_label` field already driving `MessageBubble.jsx`'s visual spinner, nothing new was added to `tool_configs`. **A real gap found and closed along the way, not part of the original ask**: Base44's socket delivers message updates by id-replace, not just by array growth. The existing Talk Mode speaking effect only triggers on array-length growth — meaning if an assistant message first arrives as an empty placeholder (a tool call running) and its final content fills in later via an in-place update to the *same* id, the length-based effect would never re-fire and Talk Mode would silently never speak the answer. Added a second, Conversational-Mode-gated effect that catches exactly that transition, coordinated with the original effect via one shared `spokenAssistantIdsRef` set so a message is never spoken twice regardless of which path sees it first. Left the original effect's structure otherwise untouched (only a two-line dedup guard added) — safer than refactoring proven, already-shipped code under the same "don't break anything" instruction.

**Real bug caught mid-implementation, not shipped**: the new `agentMessagesRef` sync effect was first written up near Conversational Mode's other new state, above where `const [agentMessages, setAgentMessages] = useState([])` is actually declared further down the component — its dependency array (`[agentMessages]`) would have referenced the variable before initialization, a genuine temporal-dead-zone crash on every render. Caught by re-reading the full file before running anything, not by the test suite (this is a render-time crash, not something a unit test over pure functions would catch) — moved the sync effect to right after the real declaration.

**What this is:** Medical tourism concierge platform. Clients book dental/aesthetic procedures with verified doctors abroad; the platform coordinates travel logistics, companions, security escorts, and post-operative recovery monitoring.

**Stack:** React 18 + Vite, React Router v6, TanStack React Query v5, Tailwind CSS, Radix UI/shadcn. Backend is Base44 BaaS — the frontend talks to it via `@base44/sdk`; ~270 Deno edge functions extend it.

### Edge Functions

Location: `base44/functions/<functionName>/entry.ts`

**A function's directory must contain only `entry.ts` — never a local copy of a shared helper, even "temporarily."** The canonical shared helpers live in `base44/shared/` (imported as `'../../shared/X.ts'`); `base44/functions/_shared/` is a dead byte-identical mirror nothing actually imports — ignore it, don't add to it. In 2026-07/08, 12 functions were given local per-directory copies of `createHandler.ts` and friends in a mistaken attempt to work around a runtime restriction — this was diagnosed by Base44 support as the actual cause of silent Cloudflare-worker 404s (function registers in the deploy record, but the extra files confuse the bundler and the worker never loads). Fixed 2026-08-02 by deleting every local duplicate and importing from `base44/shared/` like every other function. Don't reintroduce this pattern to "fix" a publish issue — the fix is always to import from `base44/shared/`, never to duplicate into the function's own folder.

All new functions must use the shared middleware:

```ts
import { createHandler, ok, err } from '../../shared/createHandler.ts';

Deno.serve(createHandler(async ({ base44, user, body }) => {
  const { field } = await body();  // lazy, single-parse, safe to call multiple times
  if (!field) return err('field is required');
  // business logic only — auth, error sanitization, request tracing are handled
  return ok({ result: 'value' });
}, { name: 'myFunction', requireAuth: true, allowedRoles: ['admin'] }));
```

`createHandler` provides: auth gate (`requireAuth` defaults to true), role guard (`allowedRoles`), lazy body parser, structured logging with function name + request ID, `X-Request-Id` / `X-Response-Time` response headers, and generic 500 error body (never leaks `error.message`).

**Never** write `Deno.serve(async (req) => {...})` directly — always use `createHandler`. Two functions genuinely bypass it for the raw, unparsed request body Stripe's signature check requires — `stripePaymentWebhook` and `stripeIdentityWebhook` — both verify via `_shared/verifyStripeSignature.ts` (shared, not duplicated) before touching the body. `handleSanctionsWebhook` does **not** bypass `createHandler` despite superficially looking similar — it uses the wrapper normally and just calls `req.text()` itself inside the handler before `body()`'s lazy JSON parse ever runs. Don't add a fourth true bypass without the same signature-verification justification.

**`allowedRoles` is a no-op when `requireAuth: false`** — `createHandler` only reads `allowedRoles` inside its `if (requireAuth)` branch, so passing both together silently protects nothing. A `requireAuth: false` function must gate itself in its own handler body: an internal `base44.auth.me()` check, a token/HMAC/session lookup, or `cronAuthorized()` (`_shared/cronAuth.ts` — admin session or `X-Cron-Secret` header, fails closed if unset). For a function called by *another edge function* with no forwardable user session (`base44.asServiceRole.functions.invoke`, common for webhook-triggered chains), use `_shared/internalAuth.ts`'s `internalOrAdminAuthorized()` instead — same fail-closed contract, but checks a body field (`internal_secret`, reusing `CRON_SECRET`) since custom headers aren't passable through `.functions.invoke()`. Never treat "no user session" alone as proof of a legitimate internal caller — that was a real vulnerability in `sendPushNotification` (fixed 2026-07-25, commit `23862dc9`).

VS Code LSP shows `Cannot find name 'Deno'` and `Cannot find module 'npm:...'` in all edge function files. These are pre-existing config gaps (no Deno type definitions) and are not real errors.

**Request body validation** (`_shared/validate.ts`, zod-based, added 2026-07-26): define a `strictObject({...})` schema (rejects unexpected fields via `.strict()` — a bare `z.object()` only strips them silently) and either pass it as `bodySchema` in `createHandler`'s options (validates before the handler runs, and `body()` then returns the validated/coerced/defaulted object — no handler changes needed) or call `validate(schema, raw)` manually when the shape depends on the payload itself (an `action`-discriminated body — use `z.discriminatedUnion`). `Fields` exports common primitives (`email()`, `shortText(max)`, `boundedInt(min,max)` — coerces `"3"`→`3`, rejects non-numeric). Only ~30 of the ~300 functions have a schema so far (the highest-risk public ones — payments, doctor/partner submissions, travel bookings, medical intake, emergency/SOS); the rest still rely on manual `if (!field)` checks and can adopt this pattern incrementally. Two deliberate exceptions with schema-free comments explaining why: `triggerCovertSOS` (a rejecting 400 would break its "always return a benign 200" security property) and signature-verified webhooks (`stripePaymentWebhook`, `handleSanctionsWebhook`, etc. — body is provider-controlled, not user input).

### Roles & RBAC

Role strings live in `src/lib/constants.js` (`ROLES` object). Role arrays live in `src/lib/roles.js` (`ADMIN_ROLES`, `CLIENT_PORTAL_ROLES`, `PARTNER_ROLES`, `DOCTOR_PORTAL_ROLES`, etc.). Never hardcode role strings — always import from one of these locations.

`ProtectedRoute` at `src/components/ProtectedRoute.jsx` handles route-level role enforcement in the frontend. Edge functions enforce roles via `allowedRoles` in `createHandler`.

## Security-Critical Systems

These areas require extra care. Changes here have audit and safety implications:

**PIN Vault** — `src/pages/EmergencyPINSetup.jsx` and related emergency pages. Client-side: PBKDF2-SHA256, 600k iterations, `morales_vault_` localStorage prefix, base64 output. Server-side: 200k iterations, `morales-pin-salt:` prefix, hex output. The two systems are intentionally different — do not conflate them.

**Audit Log Hash Chain** — `base44/functions/logAuditEvent/entry.ts`. Each audit entry stores a SHA-256 hash of the previous entry (`prev_hash`). Any deletion or modification of a log entry breaks the chain — detectable on audit. The `ALLOWED_EVENT_TYPES` Set is the authoritative allowlist.

**Passport Vault tokens** — one-time-use enforcement via `RateLimitBucket`. Token-gated routes in `tokenRoutes.jsx` are accessible without login but require a valid token from the URL.

**File uploads** — every upload call site validates type/size client-side via `validateFile()` (`src/lib/validateFile.js`) against a named preset in `UPLOAD_PRESETS` (`src/lib/constants.js`) before ever calling `Core.UploadFile`/`Core.UploadPrivateFile` — not just an `<input accept>` hint, which is a picker suggestion, not enforcement. `uploadToVault/entry.ts` re-validates server-side (the only upload path with a backend function in the middle); its `mime_type`/`file_size_bytes` checks are required fields, not conditional — a caller omitting them must be rejected, not silently skip validation. The other upload call sites go straight from the browser to Base44's storage with no backend function to add a server-side gate to. Whether uploaded files can ever be *executed* (served with a script-executable `Content-Type`, no forced download) is a property of Base44's own managed storage layer, not this repo's code — this app never builds its own file-serving path (confirmed: `downloadFromVault` only ever returns a Base44-generated signed URL, never proxies bytes or sets its own response headers; a redteam invariant guards this staying true). If it ever matters more than today, confirm directly with Base44 whether their storage buckets serve files with safe headers on both the public and private storage tiers.

**Edge function error exposure** — `createHandler` catches all unhandled errors and returns `{ error: 'An internal error occurred.' }`. Never add a catch block that re-throws `error.message` to the client.

**Entity access control (RLS)** — every `base44/entities/*.jsonc` file controls its own record-level permissions via an `"rls"` field with `read`/`create`/`update`/`delete` rules (`user_condition.role`, `user_condition.id`, `data.<field>`). **An entity with no `"rls"` block at all is fully open — any unauthenticated request can read and write every record.** When adding a new entity, always give it an explicit `rls` block matching one of the existing ownership patterns (patient-owned via `data.<owner_email_field>`, partner-owned, admin-only, or — only if a real unauthenticated page needs it, confirm via frontend grep first — deliberately public with no `rls` block at all, as `Doctor`/`DoctorPricing`/pricing-calculator entities are). Base44's deploy-time validator rejects malformed `rls` JSON for *any* function, not just the offending entity, so keep edits to the four confirmed-valid condition keys. The `User` entity (Base44's own built-in identity table) is intentionally left untouched — locking it down risks breaking login platform-wide and needs its own staged change with a rollback plan, not a batch edit.

Base44's own auto-fix bot (`base44-builder[bot]`) pushes commits titled "Apply RLS security recommendations" directly to `base44/entities/*.jsonc`, the same way it sometimes pushes direct code fixes to `src/`/`base44/functions/` — always diff these before trusting them, the same as any other bot commit. One such commit (`1a1d0adc`, 2026-07-26) added `"read": null` to `Doctor`/`DoctorPricing`/`DoctorAvailability`/`DoctorSpecialty` and 5 pricing-calculator entities that must stay public — `read: null` appears nowhere else in this repo and would have silently broken the public doctor-directory/pricing pages (`Discover.jsx`, `Providers.jsx`, `ProviderDetail.jsx` all query `Doctor` directly, client-side, with no service-role bypass). Reverted 2026-07-27. Its `create`/`update`/`delete` tightening on those entities (scoping writes to owner/admin instead of leaving them fully open) looked like a genuine improvement, but there's no confirmed-safe syntax anywhere in this repo for "rls block present, read explicitly public" — every entity with an `rls` block also has an explicit non-null `read` rule — so don't reintroduce write restrictions on these entities without first confirming that syntax with Base44 support.

## Constants & Design System

All platform-wide magic strings are in `src/lib/constants.js`: `ROLES`, `CASE_STATUS`, `PAYMENT_STATUS`, `ROUTES`, `CACHE`, `TIME`, `AUDIT_EVENTS`, and more. Import from there — do not define strings inline.

**Date formatting:** Uses `date-fns`, not `moment` (which is no longer installed). Token differences from moment: `d` (not `D`), `yyyy` (not `YYYY`), `EEE` (not `ddd`).

**Design tokens:** Background `#060B16`, card `#0C1A1D`, border `#2A3F4A`, gold accent `#D4AF37`. Font weight baseline is `font-semibold` (not `font-bold`). SF Pro system font stack via CSS `font-family`.

**Component library:** `src/components/ui/` contains shadcn/ui primitives (auto-generated — do not edit). Custom design system extensions are in `src/components/ui-system/`. Layout components are in `src/components/layout/`.

**Fuzzy matching:** All fuzzy search goes through `src/lib/fuzzyMatch.js` (`fuzzyScore`, `fuzzyMatches`, `fuzzyFilterOptions`). Never roll a local scorer — typo tolerance must behave identically everywhere ("Can't spell my name but I can book on M").

## Language / i18n

Two coexisting layers, bridged by design:

- **Engine** (`src/i18n.js`, homegrown — the npm i18next is NOT installed): 10 languages, drives global chrome via `useTranslation()`. `changeLanguage(code)` is the **single mutation point** — it persists `morales_lang` + `appLanguage` and dispatches the `languageChange` window event. Never write those keys or dispatch that event manually.
- **Wizard dictionary** (`src/lib/translations.js`): 6 languages + English fallback for the rest, consumed by the signup wizards and Booking via the `appLanguage`/`languageChange` bridge. Legacy — fold into the engine's locale files when those flows are next reworked; don't add new consumers.
